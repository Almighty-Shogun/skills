# C# Docs

Author, update, and verify C# XML documentation. This governs `///` API
documentation, not ordinary comments: a general "avoid comments" rule does not
suppress XML docs where the project documents its members. A project that uses
delimited `/** ... */` doc comments keeps that form; never convert between the
two.

## Modes

```text
csharp-docs [path ...]                  write or update docs
csharp-docs [path ...] --verify         read-only audit
csharp-docs [path ...] --verify --fix   audit, then apply approved fixes
```

`--fix` without `--verify` runs as `--verify --fix`. `--fix` expresses intent
to fix, but the findings are still shown and the corrections approved before
anything is written. A user asking for fixes after a plain `--verify` report
enters the same fix phase.

Default mode adds missing docs and corrects false or stale sentences it finds
while reading. It leaves the style of existing accurate blocks alone;
restyling is `--verify --fix` work.

Targets: a file is that file; a directory is every `.cs` file beneath it; a
`.csproj` or `.sln` is the `.cs` files of its projects. No argument targets the
`.cs` files with uncommitted changes; with none, it resolves the project from
the repository, and several plausible projects with no clear target means
asking. Generated code is never a target: files under `bin` or `obj`, `*.g.cs`
and `*.Designer.cs` files, files with an `<auto-generated>` header, and members
marked `[GeneratedCode]`. A run naming only generated files stops and says so.

An unattended run has no user to answer: `--verify --fix` then reports only
and applies no fixes, and any run stops where it would ask.

## Precedence

1. **Accuracy**: every sentence is true of the current code.
2. **Completeness**: every required member and applicable tag is present.
3. **Brevity**: the shortest block that is still true and complete.
4. **Shape**: tag order, grouping, wrapping, and voice.

Never sacrifice a higher rule for a lower one. Brevity never removes a required
tag, nor the one clause a caller needs to avoid misusing the member.

## Project standard

Read `AGENTS.md`, `CLAUDE.md`, `.editorconfig`, and any documentation
conventions, then a few documented files in the same package. Explicit
documentation rules in user or repository instructions come first, then this
standard. Where this skill allows a choice of phrasing, follow the form the
package already uses.

The project documents members when most public members in the package carry XML
docs or the project sets `GenerateDocumentationFile`. Then document every
member in scope to the same standard, private ones included unless the project
documents only its public API: types, methods, properties, fields, events,
constructors, interfaces, attributes, enum members, and extension-block
receivers. Primary-constructor parameters get a `<param>` on the type's block;
for a positional record that `<param>` is also the generated property's
documentation, so the data-carrier rule applies to it. When the project does
not document members, document the explicit target only; ask only when a run
with no argument finds an undocumented project.

A partial type's block goes on one non-generated part only, since the compiler
joins the comments of every part. A partial member's block goes on its
declaration in non-generated code.

Take `<author>` from user-level or repository-level instructions first, then
from the project's existing tags only when they all name one author; otherwise
leave it out. Never invent an author. Take `<since>` from the instructions or
the project's existing tags; with no value from either, leave the tag out.
Where the project already uses `<since>`, a new member gets
`<since>Unreleased</since>` unless the instructions name a value. An existing
member documented for the first time gets no `<since>` unless its version is
established; report it. `<since>` records when a member was added; changing its
signature or body leaves it alone.

## Verify before writing

Every sentence is a claim about the code. Read the member body, and open the
callers, collaborators, or framework behavior a claim depends on before making
it. Write only what was established; a short correct block is finished
documentation. Never invent constraints, failure modes, rationale, guarantees,
ownership semantics, or platform behavior.

A claim such as "the caller already validates this" or "this is registered as a
singleton" documents another component, even when verified there: leave it out
(see Whose contract is it).

## House style

Documentation is compact and focused. Each tag is one short line. A block grows
only when a caller would otherwise misuse the member, and detail the tag rows
below do not allow goes in a short `<remarks>`.

| Tag | Content |
|---|---|
| `<summary>` | One sentence: what the member does, or what the value is. |
| `<typeparam>` | A short noun phrase: `The application's user entity.` |
| `<param>` | A short noun phrase: `The cancellation token.` Add a clause only for behavior the caller must know: `The refresh token; unknown tokens are ignored.` |
| `<returns>` | A short noun phrase: `The service collection.` Name a meaningful null or empty case in the same phrase: `The resolved application, or <c>null</c> when scoping is disabled.` |
| `<exception>` | The condition, as a short clause: `The account is locked.` |
| `<remarks>` | One to three plain sentences, only for what the other tags cannot hold. |

A plain noun phrase is finished documentation for a parameter whose role is
obvious, such as a cancellation token, service collection, configuration, HTTP
context, or logger.

Keep out of the docs: rationale and design argument ("so a token minted for one
application cannot authenticate another"); framework internals beyond the one
clause that explains a non-obvious choice; package wiring, registration order,
and setup walkthroughs, which belong on the documentation site; lists of
callers; what a consumer does with a value; defaults already visible in the
signature; and provenance, such as how a defect was found or which version it
failed under.

Verbose, the style this standard replaces:

```csharp
/// <summary>
/// Resolves the app for the current request, refusing rather than guessing when the host is unknown.
/// </summary>
///
/// <returns>The resolved app, or <c>null</c> when scoping is off and there is nothing to resolve.</returns>
///
/// <exception cref="UnknownAppException">
/// Scoping is active and the request cannot be attributed: either the host maps to no configured application, or
/// there is no request in flight at all, as when a background job mints a token. The second carries a <c>null</c>
/// host rather than the one that failed.
/// </exception>
```

Compact:

```csharp
/// <summary>
/// Resolves the application for the current request.
/// </summary>
///
/// <returns>The resolved application, or <c>null</c> when scoping is disabled.</returns>
///
/// <exception cref="UnknownAppException">
/// Scoping is enabled and the application cannot be resolved.
/// </exception>
```

### Remarks

`<remarks>` holds what a caller or maintainer needs and the other tags cannot
carry: a caller obligation (`Callers must validate account status before
creating a session.`), a transaction or concurrency consequence (`This method
saves changes but does not start its own transaction.`), a non-obvious edge
case, the one-clause reason for a choice a future editor might undo (`Uses the
exception handler feature because exception middleware may clear the current
endpoint.`), or a pointer to the alternative (`Use <see cref="RegisterRequest"/>
for public registration.`). One plain sentence per point; never praise the
design as clean, maintainable, or flexible.

### Whose contract is it

Before writing a sentence, ask whether it would need editing if a different
type changed. If so, it documents that type: put it there when that type is in
scope, otherwise omit it and mention it in the report, and reference the type
with `<see cref="..."/>` when the reader needs the pointer. A copy of another
member's contract goes stale with no build to report it.

A data carrier (DTO, request, response, options, entity property) documents
what the value is, plus the constraints on the property itself, folded into the
summary: `The access token lifetime in minutes (1–1440).` or `The device
identified from the user agent, if available.` What a service does with the
value belongs on that service. A contract of the type as a whole, such as
validation rules declared on the type itself, is stated once in the type's
`<summary>`, not in fragments on every property.

### Exceptions

`<exception>` is required for every exception the member or an in-repository
callee throws as part of its contract. Trace direct throws, callees, reflection
or invocation wrappers, validation helpers, and parsing calls; do not infer
exceptions from names. Leave out cancellation through the caller's token and
runtime failures such as database or I/O errors. Put several conditions for one
exception in a single tag.

### Voice

- Methods use third-person singular: `Registers`, `Resolves`; a `Try` method
  `Attempts to resolve...`, which wins over the boolean form below, with the
  boolean `<returns>`.
- Types: `Represents...` for records, entities, settings, requests, and
  responses; `Provides...` for extension classes and blocks; `Defines...` for
  enums and interfaces; `Thrown when...` for exception types; what they do for
  services, handlers, attributes, delegates, and other static classes.
  Constructors start `Initializes a new instance of...`; events start `Occurs
  when...`.
- Properties state the value with no `Gets`/`Sets` prefix; a boolean property
  starts `Indicates whether...`.
- A boolean-returning method summary starts `Determines whether...`; its
  `<returns>` is `<c>true</c> if...; otherwise, <c>false</c>.`, or `Whether...`
  where the package uses that.
- A `<summary>` has no imperative voice, no "This method..." opening, and no
  second sentence.

### Returns and defaults

`<returns>` is a noun phrase, except the boolean form. Fluent receiver returns
use one fixed phrase per receiver: `The service collection.` For a result-less
`Task`, omit `<returns>` unless the package writes `A task that completes when
the response has been written.` For `Task<T>`, describe the result.

Do not restate a visible signature default. When a default changes behavior the
caller cannot infer, say what it causes: `or <c>null</c> for one second`.

### References

`<see cref>` for resolvable types and members, `<paramref>` for the current
member's parameters, `<typeparamref>` for the member's or the containing type's
type parameters, `<c>` for literals, keywords such as `<c>null</c>`, or a name
from another overload. Disambiguate overloaded crefs to avoid `CS0419`, and
confirm crefs into extension blocks with the build or generated XML.

Overrides and interface implementations use `/// <inheritdoc />`. When the
implementation adds behavior, such as an `Add` that throws
`NotSupportedException`, add the tags for it below `<inheritdoc />`, or write a
full block. Never put `<author>` or `<since>` below `<inheritdoc />`.

Document an `extension` block's receiver, when it is named, with a `<param>` on
the block: `The HTTP request.`, plus an ownership consequence such as whether a
stream stays open, when a caller must know it. A generic block gets a
`<typeparam>` for each of its type parameters.

## Shape

Tag order, omitting what does not apply:

```text
<summary> <typeparam> <param> <returns> <exception> <remarks> <author> <since>
```

Do not add `<value>`, `<example>`, `<seealso>`, `<permission>`, or `<include>`.
Keep existing ones, placed after `<remarks>` in that order.

`<param>` tags follow signature order. Separate groups with a bare `///` line:
`<typeparam>` and `<param>` form one group, `<author>` and `<since>` the last,
and every other tag type its own.

```csharp
/// <summary>
/// Creates an authenticated session and issues access and refresh tokens.
/// </summary>
///
/// <param name="user">The user receiving the session.</param>
/// <param name="app">The application scope, or <c>null</c> when unscoped.</param>
/// <param name="cancellationToken">The cancellation token.</param>
///
/// <returns>The issued tokens and their associated user.</returns>
///
/// <remarks>
/// This method saves changes but does not start its own transaction.
/// </remarks>
///
/// <author>Author Name</author>
/// <since>4.0.0</since>
```

The `<author>` and `<since>` values are illustrative; take them from the
project's tags or instructions.

`<summary>`, `<remarks>`, and `<exception>` always put the text on its own line
between the opening and closing tag. Other tags use the one-line form whenever
it fits within `.editorconfig` `max_line_length` (120 when not set), counting
indentation, `///`, and tags; otherwise they use the same block form. A tag
that needs several wrapped lines is usually too long: shorten it before
wrapping. These rules apply to new and edited blocks; do not reflow existing
text beyond what the line limit requires.

## Changing documented code

When a documented member's body changes, re-read its whole block and correct
every sentence the change falsified, not only what the compiler forces. Search
other files for docs that reference the member and fix stale claims there.
Deleting a stale sentence is always allowed; do not invent a replacement to
preserve block length. When the sentence is a required tag's only content, the
tag needs a new verified sentence.

## Code is the fact

When code and documentation disagree, the documentation is wrong. Never change
code to make a doc block true. If the documented behavior looks preferable,
report the mismatch, argue for the change on its own merits, and treat it as a
separate task that needs explicit approval.

## A defect is not a design

A doc block describes what a member does; it is never where a defect is
recorded. A verified sentence can still be the wrong sentence: when documenting
a member reveals behavior no one chose, do not write the sentence that
legitimizes it. Describing broken behavior in the register of intended behavior
turns a bug into a specification, and the next reader, including a later bug
hunt, cannot tell the two apart.

Signals: the sentence explains why something can never work, why a value never
arrives, why a supported-looking input is refused, or reads as rationale for
behavior a caller would report as broken.

Leave the block short and report the defect to the user. Silently documenting
it is wrong, and so is silently dropping it. This overrides completeness: an
exception or null return that escapes only through a defect gets no tag, and
verification reports the defect instead of `MISSING TAG`.

## Build

Build the relevant project after writing docs with
`-p:GenerateDocumentationFile=true` on the command line, without editing the
project, and treat these as documentation failures, not tolerable warnings:
`CS0419`, `CS1570`-`CS1574`, `CS1580`, `CS1581`, `CS1584`, `CS1587`,
`CS1589`-`CS1592`, `CS1658`, `CS1710`-`CS1712`, `CS1723`, `CS1734`, and
`CS1735`. Count these as failures only in the target files, and report how
many fall outside them. Exclude `CS1591` when the project does not document
its members. Report doc codes the project suppresses, such as `NoWarn` `1591`.
Inspect the generated XML when cref resolution is in doubt. A clean build does
not prove a sentence is true. When the build fails for reasons unrelated to
docs, report it and say the compiler doc checks were not obtained.

Close an authoring run with files changed, build status, defects found, claims
omitted as unverifiable, and sentences that belong on another type.

## Boundaries

Authoring edits XML documentation blocks only; `--verify` edits nothing until
fixes are approved. Leave implementation code and Git state alone, and protect
unrelated uncommitted work.

## Verification mode

These rules extend the authoring standard for `--verify`.

Verification stays independent of authoring: never trust a previous authoring
pass's conclusions, and prefer fresh verifier sub-agents for that reason. Split
large targets by project or directory across isolated sub-agents, giving each
only this standard and its scope. A verifier may read any file needed to check
a claim but reports only on its target. Start each with an explicit model and
effort level that fits its task: highest for verification and fixes.
Spot-check their actionable findings: downgrade a claim finding without
evidence to `UNCHECKED`, and re-check or drop a completeness or brevity finding
without evidence. Never describe a partial pass as complete.

### Dimensions

**Accuracy.** Read each block against the implementation it sits on and judge
each claim separately. Ask two questions: is it true, and does it describe
something anyone intended. A cref that resolves to the wrong member is
`FALSE`.

| Verdict | Meaning |
|---|---|
| `CONFIRMED` | Checked and true. Not normally reported. |
| `FALSE` | Contradicted by the code. |
| `STALE` | Names a member, parameter, type, or path that no longer exists. |
| `UNINTENDED` | True of the code, but describes a defect as designed behavior. |
| `JUSTIFICATION` | Argues the design is good without a checkable behavior. Reasoning that contradicts the code is `FALSE` or `STALE` instead. |
| `UNVERIFIABLE` | The codebase cannot settle a checkable claim. |
| `UNCHECKED` | Verification could not open what the claim depends on. |

`UNVERIFIABLE` and `UNCHECKED` are different and never merged.

**Completeness.** `MISSING DOC` for a member that requires docs and has none;
`MISSING TAG` for an absent applicable tag, including escaping exceptions,
null/empty/failure returns, and parameters. List missing docs individually, not
as a count.

**Brevity.** `VERBOSE` for a block carrying what the house style keeps out: a
multi-sentence summary, wiring or caller lists, another component's contract,
consumer behavior on a data carrier, a restated default, a tag running to
several lines of explanation, or narrating remarks. Rationale without a
checkable behavior is `JUSTIFICATION`, not `VERBOSE`. A plain noun phrase such
as `The cancellation token.` is the house style, not a finding.

**Shape.** Tag order, grouping, parameter order, one-line form and wrapping,
voice, noun-phrase returns, reference tags, `<author>`/`<since>` (none below
`<inheritdoc />`), and the extension receiver `<param>`.

### Before reporting FALSE or STALE

A false positive gets a correct doc "fixed" into a wrong one. First ask what
would make the claim true and check it: an earlier guard, a different code
path, or wording that is merely imprecise. Report only after that defense
fails, with the decisive evidence. A claim that holds only because a caller or
factory enforces it is another component's contract: report it as `VERBOSE`.

`<inheritdoc />` members stay in scope: resolve the inherited contract, check
each implementation honors it, and report a divergence against the
implementation, naming the inherited source. For cross-component claims, open
the other component. Check exceptions in both directions, flags in both states,
and that a cref which resolves still points at the right member after a
refactor. Git history is a signal, not proof.

### Report

Group by file, ordered: `FALSE`, `STALE`, `UNINTENDED`, `JUSTIFICATION`,
`UNVERIFIABLE`, `UNCHECKED`, `MISSING DOC`, `MISSING TAG`, `VERBOSE`, `SHAPE`,
then `BUILD`. Within a category, lead with what is most likely to mislead
callers or maintainers.

```text
path/Thing.cs:60  FALSE
  Claim:     "Builds the dispatch table by resolving every registered command once."
  Code:      Commands are resolved per invocation instead.
  Checked:   Thing.cs:41-58, Thing.cs:96-120.
  Ruled out: no factory or alternate constructor pre-resolves them.

path/Thing.cs:88  MISSING TAG
  Member:   Parse(string value)
  Missing:  <exception cref="FormatException">
  Checked:  Parse calls Parser.Parse at Parser.cs:31, which can propagate FormatException.

path/Thing.cs:112  VERBOSE
  Member:   AddAuth(IConfiguration configuration, bool registerExceptionHandler)
  Excess:   <param name="registerExceptionHandler"> explains package wiring and registration order.
  Compact:  "Whether to register the authentication exception handler."

path/Thing.cs:140  UNCHECKED
  Claim:    "The dispatcher has already validated the payload."
  Status:   Not established.
  Needed:   The dispatcher's source is not in the repository.
```

`STALE`, `UNINTENDED`, and `JUSTIFICATION` use the `FALSE` fields, without
`Ruled out:` except for `STALE`; `UNVERIFIABLE` uses the `UNCHECKED` fields.
`MISSING DOC` gives `Member:`; `SHAPE` and `BUILD` give `Member:` (or the
compiler code) and `Issue:`.

Close with files read, files skipped and why, counts per category, build
status, defects found in code whose docs are silent about them, and whether the
pass was complete. Say plainly when the docs are accurate throughout; never
invent marginal findings.

### `--fix`

Without `--fix`, stop after the report. With it, show each proposed
replacement or deletion before writing; the user approves per finding or all at
once. Apply only the approved corrections: re-read the code first, treat every
replacement sentence as a new claim, delete stale or unverifiable text when no
honest replacement exists, and follow the authoring standard. Fix `UNINTENDED`
and `JUSTIFICATION` by deleting the sentence; keep the defect in the report. A
finding documentation alone cannot fix stays a finding.

Then rebuild and have a fresh verifier check the corrected scope once. Report
its findings in the same form; new findings need approval before they are
fixed, and no further round follows.
